# agentlock

여러 AI 코딩 에이전트가 같은 파일을 동시에 고쳐 작업이 날아가는 걸 막습니다.

의존성 0, 파이썬 3.8+, 단일 파일 657줄. 한국어·영어 지원. [English](README.en.md)

이 저장소의 도구는 **MIT, 무료**입니다. 그대로 쓰셔도 됩니다.
배포·승인·완료 보고까지 규율을 걸어야 하신다면 유료판 **agentlock pro** 가 따로 있습니다 — [플랜과 가격 보기](https://gachi-dev.github.io/agentlock/) · [차이가 뭔가요](#이-도구가-강제하지-않는-것)

---

## 이런 적 있으신가요

터미널 두 개를 띄웠습니다. 왼쪽 에이전트에게 "결제 API 리팩터링", 오른쪽 에이전트에게 "결제 검증 로직 추가"를 시켰습니다. 둘 다 잘 돌아가는 것처럼 보입니다.

15분 뒤, 왼쪽이 `src/payment.ts` 를 통째로 다시 써서 저장합니다.
3분 뒤, 오른쪽이 **자기가 20분 전에 읽어둔 낡은 버전**에 검증 로직을 붙여서 같은 파일에 저장합니다.

왼쪽의 15분이 사라졌습니다. 그리고:

- **git이 안 알려줍니다.** 커밋 전이라 충돌도 안 납니다. 그냥 마지막에 쓴 내용만 남습니다.
- **오른쪽 에이전트도 모릅니다.** 자기가 뭘 덮어썼는지 알 방법이 없습니다.
- **당신도 모릅니다.** 둘 다 "완료했습니다"라고 보고하니까요.
- 3일 뒤에 결제가 이상하게 동작해서 `git log` 를 뒤질 때 알게 됩니다.

에이전트를 3개 이상 붙이면 이건 가끔이 아니라 자주 일어납니다. 그리고 에이전트가 늘어날수록 확률은 곱으로 올라갑니다.

agentlock은 규칙 하나만 강제합니다.

> **작업할 파일을 먼저 선언하고, 남이 선언한 파일은 건드리지 않는다.**

## 저만 겪는 일이 아닙니다

이 문제는 이미 문서로 남아 있습니다.

**Anthropic 공식 문서가 인정합니다.** Claude Code 의 Agent Teams 문서에 이렇게 적혀 있습니다.

> 두 팀원이 같은 파일을 편집하면 덮어쓰기가 발생한다. 각자 다른 파일을 맡도록 일을 쪼개라.

문제는 인정하는데 해법은 **사람이 알아서 나누라는 것**뿐입니다. 이 도구는 그 "알아서"를 코드로 옮긴 것입니다.

실제 피해 기록도 있습니다.

## git worktree 와 무엇이 다른가

지금 이 문제의 해법으로 가장 많이 이야기되는 것이 worktree 입니다. **브랜치를 나눠 병렬로 가실 거면 worktree 가 맞고, 이 도구는 그걸 대체하지 않습니다.**

worktree 가 구조적으로 못 하는 자리가 있습니다.

```console
$ git worktree add ../work-b feature-auth
fatal: 'feature-auth' is already checked out at '/path/work-a'
```

**git 은 같은 브랜치를 두 번 체크아웃하지 못하게 막습니다.** 브랜치 메타데이터가 worktree 사이에 공유되기 때문이고, 우회로가 없습니다. 즉 "한 브랜치에 에이전트 여럿"은 worktree 의 범위 밖입니다.

그런데 한 체크아웃을 공유하는 워크플로가 이미 흔합니다.

- Claude Code 의 Agent Teams 와 서브에이전트
- 한 저장소에 여러 사람이 각자 에이전트를 붙이는 경우
- CI 에서 에이전트를 돌리는 경우

여기가 이 도구의 자리입니다. worktree 를 쓰면서 같이 쓰셔도 됩니다. 서로 방해하지 않습니다.

| | git worktree | agentlock |
|---|---|---|
| 다른 브랜치로 갈라 일할 때 | **이쪽이 맞습니다** | 필요 없습니다 |
| 같은 브랜치에 에이전트 여럿 | git 이 막습니다 | **이쪽입니다** |
| 충돌을 언제 아는가 | 병합할 때 (이미 양쪽 다 작업한 뒤) | 시작하기 전 |
| 런타임·포트·DB 격리 | 안 됩니다 | 안 됩니다 |
| 의미적 충돌 | 못 잡습니다 | 못 잡습니다 |

## 설치

```bash
curl -fsSL https://raw.githubusercontent.com/gachi-dev/agentlock/main/agentlock.py -o /usr/local/bin/agentlock
chmod +x /usr/local/bin/agentlock
```

설치 스크립트를 쓰면 PATH 확인까지 알아서 합니다.

```bash
curl -fsSL https://raw.githubusercontent.com/gachi-dev/agentlock/main/install.sh | sh
```

파이썬 3.8 이상이면 됩니다. pip 설치 없음, 서드파티 패키지 없음, 데몬 없음.
`git clone` 해서 `agentlock.py` 파일 하나만 복사해도 똑같이 동작합니다.

## 60초 시작하기

아래는 실제로 돌려본 그대로입니다. (데모 저장소 경로는 `/tmp/myapp`)

**1. 저장소에 준비**

```console
$ agentlock init
준비됐습니다: /tmp/myapp/.agentlock
locks.json 과 audit.jsonl 은 커밋에 포함하세요. 팀이 같이 봐야 합니다.
```

**2. 작업 시작 전에 파일을 잡습니다**

```console
$ agentlock claim src/payment.ts src/order.ts -a agent-a -t 30m --note "결제 API 리팩터링"
확보  src/payment.ts  (30분)
확보  src/order.ts  (30분)
```

**3. 다른 에이전트가 같은 파일을 잡으려 하면 막힙니다** (종료 코드 1)

```console
$ agentlock claim src/payment.ts -a agent-b -t 20m
잡을 수 없습니다. 다른 에이전트가 작업 중입니다.
  src/payment.ts
    └ agent-a 가 src/payment.ts 를 잡고 있음 (1분 전 시작, 28분 남음)
      메모: 결제 API 리팩터링

먼저 끝나기를 기다리거나, 다른 파일부터 작업하세요.
정말 넘겨받아야 하면 --force 를 쓰되 감사 로그에 남습니다.
```

**4. 지금 누가 뭘 잡고 있는지**

```console
$ agentlock status
작업 중인 에이전트 1

  agent-a  (2개 파일)
    ● src/order.ts  1분 전 시작 / 28분 남음
        결제 API 리팩터링
    ● src/payment.ts  1분 전 시작 / 28분 남음
        결제 API 리팩터링
```

**5. 커밋 훅을 걸면 사람 실수도 막힙니다**

```console
$ agentlock install-hook
설치했습니다: /tmp/myapp/.git/hooks/pre-commit
이제 남이 잡은 파일이 섞이면 커밋이 멈춥니다.
에이전트마다 AGENT_NAME 환경변수를 다르게 주세요.
  예)  export AGENT_NAME=codex
```

```console
$ AGENT_NAME=agent-b git commit -m "결제 검증 추가"
커밋을 멈췄습니다. 남이 잡고 있는 파일이 섞였습니다.
  src/payment.ts  ←  agent-a (src/payment.ts, 28분 남음)

해결 방법
  1. 상대가 끝낼 때까지 기다린다
  2. 해당 파일만 커밋에서 빼고 나머지를 올린다
  3. 정말 넘겨받아야 하면  agentlock claim <경로> -a agent-b --force
```

**6. 끝나면 풉니다**

```console
$ agentlock release -a agent-a --all
해제  src/order.ts
해제  src/payment.ts
```

**7. 누가 언제 뭘 했는지는 전부 남습니다**

```console
$ agentlock log
2026-08-14 01:29:21  확보  agent-a      src/payment.ts
2026-08-14 01:29:21  확보  agent-a      src/order.ts
2026-08-14 01:30:33  해제  agent-a      src/order.ts
2026-08-14 01:30:33  해제  agent-a      src/payment.ts
```

## 명령어

| 명령 | 하는 일 | 자주 쓰는 옵션 |
|---|---|---|
| `init` | 현재 저장소에 `.agentlock/` 준비 | — |
| `claim <경로…>` | 파일을 잡는다 (작업 시작 선언) | `-a` 에이전트 이름(필수), `-t` TTL(기본 `30m`), `-n` 메모, `--force` 강제 회수 |
| `release [경로…]` | 락을 푼다 | `-a`(필수), `--all` 내가 잡은 것 전부, `--force` |
| `status` | 지금 누가 뭘 잡고 있나 | `--json` |
| `check [경로…]` | 커밋 전 검사. 경로를 비우면 git staged 파일을 본다 | `-a`(필수) |
| `who <경로>` | 이 파일 누가 잡고 있나 | — |
| `log` | 감사 로그 | `-n` 줄 수(기본 30), `-a` 에이전트 필터 |
| `install-hook` | git `pre-commit` 훅 설치 | `--force` 기존 훅 덮어쓰기 |

전역: `-V/--version`, `-h/--help`. 색은 TTY일 때만 켜지고 `NO_COLOR` 를 존중합니다.

**종료 코드**

| 코드 | 의미 |
|---|---|
| `0` | 성공 |
| `1` | 락 충돌로 거부됨 (`claim`, `check`, `release`) 또는 훅이 이미 있음 |
| `2` | 인자 오류 (`-t abc`), git 저장소 아님 |
| `130` | Ctrl-C |

에이전트 래퍼에서 `claim` 종료 코드만 보면 됩니다. 0이 아니면 그 파일은 건드리지 않습니다.

### 잡는 단위

경로 하나만 되는 게 아닙니다.

```bash
agentlock claim src/payment.ts        -a a1    # 파일
agentlock claim src/api               -a a1    # 디렉터리 → 하위 전부를 덮음
agentlock claim 'src/*.ts'            -a a1    # 글로브 (fnmatch)
agentlock claim src/a.ts src/b.ts     -a a1    # 여러 개 한 번에
```

디렉터리 락은 하위 파일 전부를 덮습니다. `src/api` 를 잡고 있으면 남이 `src/api/routes.ts` 를 못 잡습니다. 반대 방향도 막힙니다 — 남이 `src/api/routes.ts` 를 잡고 있으면 `src/api` 를 통째로 못 잡습니다.

글로브는 파이썬 `fnmatch` 규칙이라 `*` 가 `/` 도 건너뜁니다. `src/*.ts` 는 `src/api/routes.ts` 에도 걸립니다. 넓게 잡히는 걸 원치 않으면 경로를 명시하세요.

TTL은 `30m`, `2h`, `90s`, `1d` 형식이고, **단위 없이 숫자만 쓰면 분**입니다. `-t 45` 는 45분.

### 같은 에이전트가 다시 잡으면 연장

```console
$ agentlock claim src/payment.ts -a agent-a -t 15m
연장  src/payment.ts  (15분)
```

자기 락은 충돌로 치지 않습니다. 오래 걸리는 작업이면 주기적으로 같은 명령을 다시 부르면 됩니다. `claimed_at`(처음 잡은 시각)은 유지되고 만료 시각만 밀립니다.

## 설계 결정 3가지

### 1. 락에 TTL이 있는 이유 — 에이전트는 죽습니다

에이전트는 사람보다 훨씬 자주, 훨씬 조용히 죽습니다. 컨텍스트 초과, 레이트 리밋, 사용자가 Ctrl-C, 터미널 창을 그냥 닫음. 어느 쪽이든 `release` 는 안 불립니다.

TTL이 없으면 그 파일은 **영원히** 잠깁니다. 그리고 락 시스템이 실제로 죽는 방식은 이겁니다 — 다들 "또 그 유령 락이네" 하면서 `--force` 를 습관적으로 붙이기 시작하고, 그 순간부터 락은 아무것도 막지 못합니다.

그래서 기본 30분이고, 만료된 락은 다음 명령 실행 때 자동으로 걷힙니다. 별도 청소 데몬이 없습니다.

```console
$ agentlock status
잡혀 있는 파일이 없습니다.
(1건이 만료되어 자동 해제됐습니다)
```

TTL을 짧게 두는 건 의도적인 손해입니다. 작업이 30분을 넘기면 `claim` 을 다시 불러 연장해야 합니다. 대신 시스템에 유령 락이 안 쌓입니다.

### 2. 감사 로그가 append-only인 이유 — 사고 났을 때 필요한 건 현재 상태가 아니라 순서입니다

`locks.json` 은 **지금** 상태만 압니다. 그런데 문제가 터졌을 때 알아야 하는 건 "지금 누가 잡고 있나"가 아니라 **"내 코드가 어느 시점에 왜 날아갔나"** 입니다.

`.agentlock/audit.jsonl` 은 한 줄에 한 사건씩 붙이기만 합니다. 지우거나 고치는 코드 경로가 없습니다.

```json
{"ts": "2026-08-14T01:29:21+00:00", "action": "claim", "pid": 11921, "path": "src/payment.ts", "agent": "agent-a", "ttl": 1800, "note": "결제 API 리팩터링"}
{"ts": "2026-08-14T01:30:33+00:00", "action": "release", "pid": 11934, "path": "src/payment.ts", "agent": "agent-a"}
```

기록되는 사건은 `claim` / `renew` / `release` / `expire` / `steal` 다섯 가지입니다. 특히 `steal`(강제 회수)이 중요합니다.

```console
$ agentlock claim src/api/routes.ts -a a2 -t 10m --force
강제 회수: src/api (a1 → a2)
확보  src/api/routes.ts  (10분)

$ agentlock log
2026-08-14 01:25:59  확보  a1           src/api
2026-08-14 01:25:59  확보  a2           src/api/routes.ts
2026-08-14 01:25:59  강제회수  a2           src/api  (a1 로부터)
```

`--force` 를 막지 않는 대신 반드시 흔적을 남깁니다. 급할 때 뚫을 길이 없으면 사람들은 도구를 아예 안 쓰기 시작합니다. 뚫을 수는 있게 하되, 나중에 "누가 뚫었지"를 30초 안에 찾을 수 있게 하는 편이 낫습니다.

`jq` 로 바로 파싱됩니다.

```bash
jq -r 'select(.action=="steal")' .agentlock/audit.jsonl
```

### 3. `locks.json` 을 git에 커밋하는 이유 — 락이 로컬에만 있으면 옆자리는 못 봅니다

`init` 이 만드는 `.agentlock/.gitignore` 는 이렇게 생겼습니다.

```gitignore
.guard
*.tmp
*.corrupt
```

즉 프로세스 간 가드 파일과 임시 파일만 빼고, **`locks.json` 과 `audit.jsonl` 은 커밋 대상**입니다. 의도한 겁니다.

락이 `.gitignore` 안에 있으면 내 머신에서만 보입니다. 그런데 에이전트는 한 머신에만 있지 않습니다. CI에서 돌기도 하고, 팀원 노트북에서 돌기도 하고, 원격 세션에서 돌기도 합니다. 커밋해 두면 `git pull` 한 사람 전부가 같은 상태를 봅니다.

부작용으로 세 가지가 딸려옵니다.

- 락 자체가 코드 리뷰 대상이 됩니다. PR 디프에서 "이 에이전트가 왜 `src/` 를 통째로 잡았지"가 보입니다.
- 감사 로그가 커밋 히스토리와 같은 타임라인에 놓입니다. "이 커밋 직전에 누가 뭘 강제 회수했나"를 바로 볼 수 있습니다.
- `locks.json` 자체가 충돌할 수 있습니다. 이건 오히려 안전합니다. 파일 내용이 조용히 사라지는 것보다 **git이 시끄럽게 멈추는 편**이 낫습니다. 키가 경로별로 분리돼 있어 대부분 자동 병합됩니다.

같은 머신 안에서는 `.agentlock/.guard` 가 처리합니다. `O_EXCL` 스핀락이라 리눅스/맥/윈도우에서 똑같이 동작하고, 죽은 프로세스가 남긴 가드는 30초 뒤 자동 회수됩니다. `locks.json` 은 임시 파일에 쓰고 `fsync` 후 `os.replace` 로 갈아끼워서, 쓰는 중에 죽어도 반쪽짜리 파일이 남지 않습니다.

## 실전에서 쓰는 법

### 에이전트마다 이름을 다르게

훅은 `AGENT_NAME` 환경변수를 봅니다. 없으면 `git config user.name` 으로, 그것도 없으면 `unknown` 으로 떨어집니다. 모든 에이전트가 `unknown` 이면 서로를 구분하지 못해 아무것도 막지 못합니다.

```bash
# 에이전트 A 터미널
export AGENT_NAME=agent-a

# 에이전트 B 터미널
export AGENT_NAME=agent-b
```

### 잡는 범위는 좁게, TTL은 짧게

`agentlock claim . -a me -t 8h` 는 문법적으로 되지만, 저장소 전체를 8시간 잠그는 건 락이 아니라 그냥 통행 금지입니다. 다른 에이전트가 아무것도 못 하게 되면 사람들은 곧 `--force` 를 기본으로 쓰기 시작합니다.

실제로 고칠 파일만, 실제로 걸릴 시간만 잡는 게 훨씬 잘 굴러갑니다.

### 운영해 보니

에이전트 8종이 한 저장소에 붙어 55일 무중단으로 돌아가는 환경에서 나온 도구입니다. 그 규모에서 실제로 문제가 됐던 건 락 알고리즘이 아니라 이 두 가지였습니다.

- 유령 락 (에이전트가 죽고 release를 안 부름) → TTL로 해결
- 아무도 `--force` 를 누가 언제 썼는지 모름 → 감사 로그로 해결

그래서 이 도구에는 큐도, 우선순위도, 대기 알림도 없습니다. 없어도 됐습니다.

## FAQ

### 파일 락(`flock`, `.lock` 파일)이랑 뭐가 다른가요

**막는 대상이 다릅니다.** OS 파일 락은 프로세스가 파일 디스크립터를 여는 순간에 걸리고, 프로세스가 죽으면 커널이 바로 풉니다. 그런데 코딩 에이전트는 파일을 열어놓고 붙잡고 있지 않습니다. **읽고 → 닫고 → 몇 분 동안 생각하고 → 다시 열어서 씁니다.** 위험한 구간은 파일이 닫혀 있는 그 몇 분입니다. `flock` 은 이 구간을 전혀 보호하지 못합니다.

agentlock은 파일 디스크립터가 아니라 **의도**를 잠급니다. "나 이거 30분 동안 고칠 거야"를 선언하는 거라, 파일을 안 열고 있어도 유효합니다.

나머지 차이:

| | OS 파일 락 | agentlock |
|---|---|---|
| 유효 구간 | fd가 열려 있는 동안 | 선언한 TTL 동안 |
| 누가 잡았는지 | 알기 어려움 | `agentlock who` |
| 이력 | 없음 | append-only 감사 로그 |
| 다른 머신에서 보임 | 안 보임 | git으로 공유 |
| 강제성 | 커널이 강제 | 협조적 (훅으로 보강) |

마지막 줄이 정직한 한계입니다. agentlock은 **협조적(advisory) 락**입니다. `agentlock claim` 을 안 부르고 그냥 `vim` 으로 파일을 고치면 아무것도 못 막습니다. 그래서 `install-hook` 이 있습니다. 커밋 시점에 한 번 더 걸러 주고, 이게 실질적인 마지막 방어선입니다.

### 사람 팀에도 쓸 수 있나요

됩니다. 에이전트 이름 대신 사람 이름을 넣으면 그대로 동작합니다.

```bash
agentlock claim src/checkout/ -a minsu -t 2h --note "결제 플로우 개편, PR #412"
```

특히 이런 경우에 쓸 만합니다.

- 대규모 리팩터링 중 "이 디렉터리 지금 건드리지 마세요"를 슬랙 대신 저장소에 박아둘 때
- 자동 생성되는 파일(마이그레이션, 스키마, 락파일)을 누가 재생성 중인지 알려야 할 때
- 사람과 에이전트가 섞여서 같은 저장소를 만질 때 (이게 사실 제일 자주 사고 납니다)

다만 사람은 에이전트보다 작업 시간이 훨씬 기니까 TTL을 넉넉히 주세요. 그리고 이건 브랜치 전략을 대체하지 않습니다. 같은 브랜치 위에서 동시에 일할 때 쓰는 도구입니다.

### 에이전트가 이 명령을 자동으로 부르게 하려면

에이전트의 시스템 프롬프트(혹은 저장소 루트의 에이전트 지침 파일)에 이걸 넣으세요.

```markdown
## 파일 락 규칙 (반드시 지킬 것)

이 저장소는 여러 에이전트가 동시에 작업한다. 파일을 수정하기 전에 반드시 락을 잡는다.

1. 파일을 수정(생성/편집/삭제)하기 전에 실행한다.
       agentlock claim <경로…> -a <내_에이전트_이름> -t 30m --note "<무슨 작업인지 한 줄>"

2. 종료 코드가 0이 아니면 그 파일을 절대 수정하지 않는다.
   출력에 누가 잡고 있는지 나온다. 사용자에게 그대로 알리고,
   락이 걸리지 않은 다른 파일부터 작업하거나 작업을 멈춘다.
   사용자가 명시적으로 지시하기 전에는 --force 를 쓰지 않는다.

3. 작업이 30분을 넘길 것 같으면 같은 claim 명령을 다시 실행해 연장한다.

4. 파일 수정이 끝나면 즉시 푼다.
       agentlock release <경로…> -a <내_에이전트_이름>
   세션을 마칠 때는  agentlock release -a <내_에이전트_이름> --all

5. 남이 뭘 잡고 있는지 궁금하면  agentlock status
   특정 파일만 확인하려면      agentlock who <경로>
```

`<내_에이전트_이름>` 은 에이전트마다 다르게 고정하세요. 여기가 겹치면 서로를 같은 에이전트로 봐서 충돌 검사가 통과해 버립니다.

한 가지 현실적인 조언: 에이전트는 규칙을 잊습니다. 그래서 프롬프트만 믿지 말고 `install-hook` 을 같이 거세요. 프롬프트는 사고를 줄이고, 훅은 사고가 커밋으로 넘어가는 걸 막습니다.

### 락 파일이 깨지면요

`locks.json` 이 깨진 JSON이면 조용히 무시하지 않고 `locks.json.corrupt` 로 옮긴 뒤 경고를 내고 빈 상태에서 다시 시작합니다. 조용한 실패가 제일 위험하기 때문입니다.

```
경고: 락 파일이 깨져서 <저장소>/.agentlock/locks.json.corrupt 로 옮기고 새로 시작합니다.
```

깨진 파일은 지우지 않고 `.corrupt` 로 남겨 두니, 무슨 일이 있었는지는 나중에 열어 볼 수 있습니다.

### `.agentlock/.guard` 가 남아서 명령이 안 돌아갑니다

30초가 지나면 자동으로 회수합니다. 그 전에 급하면 메시지에 나온 경로를 그냥 지우면 됩니다.

```
다른 프로세스가 .agentlock 를 잡고 있습니다. 계속 이러면 <경로>/.agentlock/.guard 를 지우세요.
```

### 이미 pre-commit 훅을 쓰고 있는데요

`install-hook` 은 기존 훅을 덮어쓰지 않고 멈춥니다 (종료 코드 1).

```
이미 pre-commit 훅이 있습니다: <경로>/.git/hooks/pre-commit
덮어쓰려면 --force 를 쓰세요.
```

기존 훅에 한 줄만 추가해도 됩니다.

```sh
agentlock check -a "${AGENT_NAME:-$(git config user.name)}" || exit 1
```

경로를 비우면 `git diff --cached` 로 staged 파일을 알아서 봅니다.

## 화면 언어

한국어와 영어로 나옵니다. `AGENTLOCK_LANG` 에 `en` 또는 `ko` 를 주면 됩니다.

```bash
export AGENTLOCK_LANG=en
```

정하지 않으면 쓰는 환경의 언어를 따라갑니다. 한국어 환경이면 한국어로 나옵니다. 번역이 없는 문장은 원문이 그대로 나오므로, 번역표를 고쳐도 도구가 멈추지 않습니다. 번역표는 `agentlock.py` 맨 아래 `EN` 에 그대로 있습니다. 팀에서 쓰는 말투로 바꿔 쓰셔도 됩니다.

`locks.json` 과 `audit.jsonl` 에 쌓이는 내용은 언어와 무관하게 같습니다. 팀원마다 언어 설정이 달라도 같은 기록을 봅니다.

## 이 도구가 강제하지 않는 것

agentlock은 운영 규율 아홉 가지 중 3번(작업 시작 선언) 하나만 코드로 옮긴 것입니다. 에이전트 8종을 한 저장소에 붙여 55일 돌리면서 남은 규율은 이렇습니다.

1. 역할 고정 분리
2. 파일 소유권과 인터페이스 계약
3. **작업 시작 선언** — 이 도구가 강제하는 것
4. 단일 배포자
5. 부재 시 승계
6. 정체성 고정 프롬프트
7. 완료 보고 검증 의무
8. 승인 게이트
9. append-only 원장

나머지 여덟 개는 이 도구가 막지 않습니다. 배포가 두 번 나가는 것, 검증하지 않은 완료 보고, 대화 창이 끊긴 뒤의 승계는 3번으로 안 막힙니다.

그쪽까지 필요하시면 이 저장소 바깥에 따로 정리해 뒀습니다.

**agentlock pro** — 아홉 가지를 전부 코드로 강제합니다. `setup` 한 번으로 역할·소유권·배포 담당 지정과 git 훅 설치가 끝납니다. 남의 담당 파일은 커밋이 막히고, 완료 보고에서 미검증 항목을 비우면 거부되고, 배포는 지정된 한 명이 사람 승인을 받아야 실행되고, 기록은 해시로 엮여 있어 고치면 몇 번째 줄이 훼손됐는지 잡아냅니다. 규율 아홉 가지 전문, 에이전트 정체성 프롬프트 템플릿 3종, 양식 5종, 충돌 사고 대응 절차, 도입 체크리스트를 묶은 **문서 킷도 함께 들어갑니다.** 따로 사실 필요 없습니다.
